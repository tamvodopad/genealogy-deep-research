# Приём: проверка возможностей, анкета, инвентарь

Читать: в самом начале, до анализа.

## 1. Проверка возможностей (молча, без вопросов пользователю)
- Есть ли браузерные инструменты (Chrome): нужны для РГИА, ЕАИС, сайтов под входом. Нет → такие источники в плане помечать `needs_browser` и в отчёте давать пользователю инструкцию «откройте сами».
- Есть ли инструмент Workflow (оркестрация многих агентов по скрипту) — иначе Agent пачками по ≤ 5.
- `python3 -I -c "import openpyxl, xlrd"` — для таблиц .xlsx/.xls (нет → предложить `pip install`, не ставить самому без согласия).
- Где пользователь географически (из контекста/спросить в анкете): часть российских ресурсов закрыта из-за границы.
- Работаем ли внутри Obsidian-хранилища или другого проекта с правилами (CLAUDE.md): если ресерч для владельца этого хранилища — отчёт оформлять по его правилам; если для другого человека — отдельная папка, правила хранилища не применять.
- Браузер — это сессии и входы владельца компьютера: под ними работать только для него самого.

## 2. Входные данные
- **Есть GEDCOM** → `python3 -I SKILL_DIR/scripts/gedcom_profile.py TREE.ged DIR/profile` (древо > 2 000 персон — `--top 40`). Из «Древа Жизни»: Файл → Экспорт → GEDCOM, кодировка UTF-8. Нативный файл программы не читаем — попросить экспорт.
- **Нет древа или в древе < 50 персон с местами** → вся анкета ниже (одним сообщением). Если profile.md нет — ответы записать в `DIR/intake.md` в его структуре (места, фамилии, стены); если есть — в intake.md только то, что сверх древа.
- **Таблицы баз** (Excel/CSV от поисковых групп) → сложить в отдельную папку, гонять `SKILL_DIR/scripts/table_search.py` на шаге ресерча (трек T3).

## 3. Анкета (древо с ≥ 50 персонами с местами — пункты 5–9; иначе вся)
1. Фамилии рода (все известные написания, «он же», девичьи фамилии).
2. Населённые пункты: название, уезд/губерния или современный район/область; годы, когда там жили.
3. Самые ранние известные предки по каждой линии: ФИО, годы, место.
4. Вера/народ/сословие, если известно (православные, старообрядцы, крещёные татары, удмурты, мари, чуваши…; государственные/удельные/помещичьи/заводские крестьяне, казаки, мещане).
5. Что уже на руках: сканы ревизий/метрик, архивные справки, прошлые отчёты, таблицы заказов (пути к папкам/файлам).
6. Что уже заказано и где (чтобы не дублировать).
7. Бюджет на платные заказы в архивах (0 — только бесплатные онлайн-источники).
8. Где вы находитесь (из-за блокировок) и есть ли доступ с российского IP.
9. Глубина: быстрый / стандартный / глубокий ресерч (см. SKILL.md) и куда положить отчёт.

## 4. Инвентарь «что уже есть» → `DIR/known.jsonl` (обязательно до ресерча)
По строке JSON на элемент: `{"kind": "cipher|file|claim", "value": "…", "archive": "<каноническое имя архива>", "where": "…"}`. Имя архива — полное, одинаковое в инвентаре и находках (аббревиатуры бывают омонимами: ГАТО — Тамбовский и Томский).
- Из таблиц заказов пользователя: каждый шифр (`kind: cipher`) с пометкой статуса.
- Из папок со сканами: имена папок/файлов по деревням и видам документов (`kind: file`).
- Из прошлых отчётов/заметок: ключевые установленные факты (`kind: claim`) и шифры.
- Из GEDCOM: источники `SOUR`/`PAGE` у персон (они уже в people.json → поле `sources`).
Полнота по каждому архиву — отдельной строкой: `{"kind": "scope", "value": "Государственный архив Кировской области", "aliases": ["ЦГАКО", "ГАКО"], "where": "complete"}` (пользователь подтвердил, что всё по этому архиву перечислено) или `"partial"`. Находки по архиву без `complete` получают `inventory_status: unknown`, а не `new`. Пустой инвентарь допустим: «у меня ничего нет» → `{"kind": "scope", "value": "*", "where": "complete"}`.
